Personal projects, in depth

Problem

Wanted to understand how a RAG system behaves end-to-end, without leaning on a hosted API to hide the hard parts — chunking, retrieval quality, and grounding a model's answers in real documents rather than its own training data.

Approach

Built the full pipeline myself: document ingestion, chunking, embedding generation, vector storage, semantic retrieval, and contextual response generation — run against locally hosted models instead of a paid API.

Architecture

Node.js orchestration layer coordinates ingestion and retrieval; embeddings are stored in a vector database and queried via semantic similarity search before being passed as context to the local model for response generation.

Hardest part

Getting retrieval relevant enough without a hosted, pre-tuned embedding model — most of the iteration went into chunking strategy and tuning similarity search rather than the LLM call itself.

Problem

Small tailoring/boutique businesses juggle customer measurements, custom orders, billing and delivery across notebooks, WhatsApp threads and spreadsheets — there's no off-the-shelf software built around how a made-to-order garment actually moves from measurement to delivery.

Approach

Designed one system around that workflow: customer management, measurement records, order tracking, billing, payments and delivery, instead of bolting a generic inventory tool onto the business.

Architecture

Full-stack app with a workflow-first data model — each order carries its own lifecycle state rather than treating tailoring like standard retail inventory. Built with AI-assisted development practices to move faster through CRUD-heavy scaffolding.

Hardest part

Modeling the order lifecycle (measurement → stitching → fitting → delivery) flexibly enough to handle different garment types without the schema turning into a special case for every product.
